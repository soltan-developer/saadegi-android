# استاندارد تست سرعت سادگی — V1 (۱۴۰۵/۰۷/۲۷)

## هدف

کاربر باید *کیفیت واقعی یک کانفیگ* را ببیند، نه سرعت عمومی اینترنت تلفن. در نسخه اول تست سرعت **تک‌سروری** است؛ تست هم‌زمان سرعت تمام کانفیگ‌ها عمداً حذف شده تا مصرف حجم و فشار به سرورها کنترل شود.

## شرط نمایش دکمه

۱. کاربر یک سرور را از سابسکریپشن انتخاب می‌کند.  
۲. همان سرور باید در تست HTTP تأخیر Xray حداقل یک موفقیت داشته باشد. نتیجه بیش از ۹۰ ثانیه اعتبار نمایشی ندارد.  
۳. آنگاه دکمه «تست سرعت همین سرور — ۵ MiB» برای همان سرور نشان داده می‌شود.  
۴. لحظه شروع دانلود، Xray یک HTTP probe جدید روی همان کانفیگ اجرا می‌کند؛ در صورت شکست، دانلود انجام نمی‌شود.

**مهم:** در این مرحله «سرور انتخاب‌شده و سالم در یک آزمایش» با «VPN متصل سراسری» یکی نیست. تا زمان فعال‌شدن VpnService، دکمه فقط تست یک proxy از طریق هسته موقت Xray است. پس از اجرای موتور VPN، به‌جای شروع یک runXray دیگر، دانلود از Network اختصاصی VPN خود اپ انجام خواهد شد (Network.openConnection و اعتبارسنجی اتصال فعال)؛ به اینترنت مستقیم گوشی fallback نمی‌کنیم. اجرای runXray تشخیصی هم‌زمان با هسته VPN ممنوع است.

## الگوریتم فعلی

- فقط یک کانفیگ در هر نوبت؛ با نمونه HTTP HEAD از داخل Xray بازسنجی شود.
- موتور موقت Xray با SOCKS محدود به loopback 127.0.0.1، خروجی همان کانفیگ.
- درخواست HTTPS به فایل ۵ MiB از Cloudflare با query اندازه ثابت؛ redirect و cache و compressed content غیرفعال.
- شمارش حداکثر ۵٬۲۴۲٬۸۸۰ بایت (=5 MiB ≈5.24 MB). اگر Content-Length صریح با این اندازه تطبیق نکند، خطا نمایش داده شود.
- اگر HTTP status != 200، فایل ناقص، سرور زمان‌تمام‌شده، فایل بزرگ‌تر یا طول نادرست: **هیچ سرعتی به‌عنوان موفقیت نمایش داده نشود**.
- زمان با monotonic clock اندازه‌گیری شود (از شروع درخواست تا پایان دریافت). نتایج: Mbps = bytes × 8 / seconds / 1e6 و MB/s = bytes / seconds / 1e6؛ عددها واحد متفاوت دارند.
- کمتر از ۲ ثانیه زمان انتقال = «نمونه کوتاه و تقریبی»، نه سرعت پایدار قطعی.
- حد زمانی کلی ۳۰ ثانیه + timeout شبکه؛ در failure صرفاً خطای فارسی بدون URI/token.
- قبل از تست، رضایت صریح بابت مصرف حجم گرفته شود.
- بدون تست سرعت موازی؛ نتیجه هر سرور فقط به همان profile ID تعلق دارد.

## محدودیت‌ها و کنترل‌های ضروری آزمون دستگاه

- این روش **quick single-stream throughput** است؛ بر خلاف speedtestهای چندجریانی طولانی‌تر، بیشینه ظرفیت شبکه را تضمین نمی‌کند. CDN مسیر سرور و اپراتور می‌تواند نتیجه را تغییر دهد.
- قطعی پروکسی نباید باعث direct fallback شود؛ روی گوشی با قطع کانفیگ و کنترل مصرف/آی‌پی آزمون شود.
- پاسخ HTTPS از طریق SOCKS لازم است. رفتار DNS و proxy در Android نسخه‌های هدف باید در تست‌های واقعی بررسی شود.
- local SOCKS بدون احراز هویت فقط هنگام تست کوتاه‌مدت روشن است؛ محدود به localhost و با cleanup قطعی.
- هنوز تست عملی موبایل روی حداقل دو اپراتور و دو گوشی انجام نشده. Build PASS جایگزین تست اتصال واقعی نیست.
- در Android که VPN فعال است، تست از مسیر Network اختصاصی VPN یا کنترل امن هم‌ارز باید انجام شود؛ در حال حاضر این مسیر **پیاده‌سازی نشده** است.
- اگر نمایش فقط برای «سرور متصل» مدنظر باشد، بعد از تأیید کامل VpnService شرط UI را با وضعیت CONNECTED و تطبیق profileId عوض کنیم.

## مطالعات تطبیقی

- v2rayNG RealPing: استفاده از measureOutboundDelay بعد از غربال احتمالی TCP.
- Mihomo URLTest: health checks، tolerance و batch concurrency.
- sing-box URLTest: HTTP HEAD و کنترل warm-up و history.
- تست سرعت محدود به یک سرور در این مرحله برای کاهش هزینه حجم بهتر از تست همه کانفیگ‌ها است.
